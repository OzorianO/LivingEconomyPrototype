Правки слід звіряти з поточним кодом D: перед копіюванням; уникати дрейфу копій.

Наявна межа: ядро не використовує Unity API, але поточний планувальник дня
живе у SettlementView і залежить від прибуття всіх NPC. Швидка симуляція
викликає ті самі команди з іншим порядком покупців. Це потребує уточнення
перед автономним наймом та складною навігацією.

Ціль: конфігурація сценарію, бізнеси/власники, вакансії й призначення як дані;
команди найму і торгівлі перевіряються ядром; явний порядок подій та правила
для недоступних цілей. UI відображає реальні посади й кількість працівників.
Збереження має підтримувати змінні призначення та міграцію версій.

Поточний XML v2 містить завершений день, рахунки, інвентарі, голод,
визначення бізнесів, змінні посади, параметри і журнал. XML v1 підтримується
міграцією. Стан посеред маршруту не підтримується.
Детальна послідовність змін: ROADMAP.md, етапи 3–4.

Перевірки staging-копій з `My Game`:
`dotnet run --project Implementation/Checks/Checks.csproj`.
Властивість MSBuild `SimulationSourceDirectory` дозволяє перевіряти
оригінальні файли на D: із результатами збірки в робочій папці.

Оновлення автономності: правила черги й розв'язання невдалих цілей тепер
у DailySimulation. Прибуття лише реєструється; FinishWork/FinishShopping/
FinishDay виконують дії у щоденній черзі. SettlementView повідомляє
прибуття/невдалий маршрут і обмежує його активним таймаутом.
Самостійний найм відбувається перед початком руху, причини у журналі.
Поточне збереження — XML v3, сумісне з v1/v2; старі файли зберігають
ручний режим найму. Деталі: AUTONOMY_PROGRESS.md.

ReloadCheckpoint у SimulationSave.cs зберігає XML-рядок завершеного дня
в серіалізованому полі SimulationPreview. OnDisable/OnEnable забезпечують
відновлення після перезавантаження; прямі Unity-посилання/словники карти
перебудовуються з ядра. GeneratedSettlement містить створені об'єкти,
щоб прибирати лише їх при повторній ініціалізації. Дисковий слот не змінюється.
Політика перерваного дня та перевірки: UI_RELOAD.md.
